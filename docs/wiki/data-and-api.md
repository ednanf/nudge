# Data model and API

## OpenAPI specification

[OpenAPI.yaml](../../OpenAPI.yaml) is the self-contained OpenAPI 3.1.1 contract for all eleven operations across nine paths. Import it into a compatible API client or documentation tool. It describes session cookies, the separate cron bearer secret, origin requirements, request validation, defaulted configuration, response shapes and error statuses.

The server entry defaults to `http://localhost:5173/api`. Replace it with your own installation's API base URL when importing; production deployment addresses are intentionally absent. Paths in the specification omit the `/api` prefix because it is already part of the server URL.

For protected calls, first log in and retain `Set-Cookie` in the client's cookie jar. Browser writes require `Origin` and `Content-Type: application/json`, even on DELETE/manual-check/logout requests whose bodies are ignored. Sending `{}` helps imported clients include the JSON media type. The browser sets Origin itself: an externally hosted documentation UI cannot bypass same-origin restrictions by manually setting this header.

The cookie lifetime is seven days by default or thirty with `rememberMe: true`. Cron uses `Authorization: Bearer <CRON_SECRET>` instead of a session. A remote check failure still returns HTTP 200 with `success: false`; do not infer success solely from the HTTP status.

Validate the schema without installing application dependencies:

```sh
npx --yes @redocly/cli lint OpenAPI.yaml --extends spec
```

The optional recommended lint profile reports two expected style advisories: a local-development server URL, and the session-status endpoint having no 4xx response. Those reflect intentional behavior; signed-out session introspection returns 200 with `authenticated: false`. Do not add fictional error responses just to silence an advisory. Update the specification alongside route/schema changes and republish this Wiki when its source changes.

## Storage conventions

The database is SQLite-compatible and accessed with parameterized libSQL queries. IDs are UUIDs generated by Node. Timestamps and durations are integers in milliseconds; database booleans are `0`/`1` and API booleans are JSON booleans. API timestamps are epoch milliseconds, except the schedule/slot strings described below.

The complete initial DDL is in [001_initial.sql](../../migrations/001_initial.sql). There is no ORM or generated model layer.

## Tables

| Table          | Fields and purpose                                                                                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `projects`     | `id` primary key; `name`; JSON text `config`; encrypted JSON envelope `secrets`; `enabled`; `created_at`; `updated_at`                                                   |
| `checks`       | `id` primary key; `project_id` foreign key; `started_at`; `trigger` (`manual`/`scheduled`); `success`; sanitized nullable `error`; `duration_ms`; nullable weekly `slot` |
| `sessions`     | `token_hash` primary key; `expires_at`; `admin_version`, the SHA-256 digest of the configured administrator hash                                                         |
| `login_limits` | Fifteen-minute `bucket` primary key; `attempts`; `expires_at` for cleanup                                                                                                |
| `leases`       | Lock `name` primary key; random invocation `owner`; `expires_at`                                                                                                         |
| `cron_runs`    | Weekly `slot` primary key; `started_at`; nullable `finished_at`                                                                                                          |

`checks` has a unique `(project_id, slot)` constraint. Scheduled rows use a Monday-noon UTC ISO string; manual checks use SQL NULL and can have multiple rows for the same project. SQLite's NULL uniqueness behavior is intentional here.

Indexes support checks by project/time, checks by time, session expiry and rate-limit cleanup. The schema declares project/check foreign-key cascading; the delete route also explicitly deletes checks and the project in one write batch, without relying on a remote connection retaining PRAGMA state.

`config` contains the public endpoint/request settings. Decrypting `secrets` yields `{ username, password, authBody }`. No extracted authentication tokens, response cookies or external response bodies are stored.

## API conventions

The browser calls the same origin under `/api`. Responses are JSON and are not cached. Browser writes require `Content-Type: application/json` and an exact trusted `Origin`. Protected routes additionally require the `nudge_session` cookie.

Cron uses `Authorization: Bearer <CRON_SECRET>` independently of browser sessions. Never expose that secret in client code.

| Route                          | Access                   | Behavior                                                                                           |
| ------------------------------ | ------------------------ | -------------------------------------------------------------------------------------------------- |
| `POST /api/auth/login`         | Trusted origin           | Verify `{ "password": "...", "rememberMe": true/false }`, apply rate limit, issue a session cookie |
| `POST /api/auth/logout`        | Session + trusted origin | Delete the session and expire its cookie                                                           |
| `GET /api/auth/session`        | Public                   | Return `{ "authenticated": true/false }`                                                           |
| `GET /api/projects`            | Session                  | Return projects, next execution and latest cron-run timestamps                                     |
| `POST /api/projects`           | Session + trusted origin | Validate/encrypt/create; HTTP 201                                                                  |
| `PATCH /api/projects/:id`      | Session + trusted origin | Replace editable configuration, or update only `enabled`                                           |
| `DELETE /api/projects/:id`     | Session + trusted origin | Delete project/history under the execution lease                                                   |
| `POST /api/projects/:id/check` | Session + trusted origin | Run and persist a manual check                                                                     |
| `POST /api/projects/test`      | Session + trusted origin | Test an unsaved configuration; optional existing `id` preserves saved credentials                  |
| `GET /api/checks`              | Session                  | Return the latest 100 execution records                                                            |
| `GET /api/cron`                | Cron bearer secret       | Run enabled projects for the current weekly slot                                                   |

`rememberMe` is optional and defaults to false. True sets both cookie and stored session expiry to thirty days; false or omission keeps seven days. Non-boolean values return 400 before attempting password verification. Logout and administrator-hash changes invalidate either session type. No database migration is required because sessions already store their own expiration timestamps.

There are no registration, account-management, recovery or OAuth routes. History has no pagination or per-project query filter in this version.

## Project request

This example contains placeholders only:

```json
{
  "name": "Portfolio API",
  "enabled": true,
  "username": "disposable@example.com",
  "password": "<disposable-password>",
  "authBody": {},
  "config": {
    "baseUrl": "https://api.example.com",
    "authPath": "/api/auth/login",
    "authMethod": "POST",
    "usernameField": "email",
    "passwordField": "password",
    "authMode": "bearer",
    "tokenPath": "data.accessToken",
    "keepAlivePath": "/api/me",
    "keepAliveMethod": "GET",
    "keepAliveBody": null
  }
}
```

A normal PATCH supplies the complete name/configuration and may omit saved credential fields. It is not a general partial-object merge. The special payload `{ "enabled": false }` updates just the schedule switch.

New projects need a username and password. For an existing project, omitted username/password/authBody retain their saved values; empty strings are not valid API replacements. Send `authBody: {}` to clear extra login fields.

Unsaved tests use the same payload, optionally adding `id` for a saved project. They return `{ success, error, durationMs }` without storing history.

## Validation details

The authoritative schemas are in [server/validation.ts](../../server/validation.ts):

- Project name: trimmed, 1–80 characters. Username: 1–320 characters. Password: 1–1024 characters. Usernames are not restricted to email syntax.
- API origin: HTTPS, port 443, no embedded credentials, path prefix, query or fragment; maximum 512 characters.
- Paths: absolute path beginning with a single `/`, maximum 512 characters; no backslashes, CR/LF or fragments.
- Credential field names: flat alphanumeric/underscore keys beginning with a letter; selected prototype-related names are rejected; username and password keys must differ.
- Token path: dot-separated alphanumeric/underscore keys, up to 128 characters.
- Extra login and keep-alive JSON: objects, not arrays, each up to 8,192 UTF-16 code units after `JSON.stringify`. Keep-alive JSON may be null.
- Unknown project/configuration keys are rejected.
- Incoming request bodies are capped at 32 KB before JSON parsing.

Endpoint origins and public IPs are checked again during execution. Saving a syntactically valid private-IP URL does not authorize connecting to it; execution rejects it.

## Response shapes

Project responses expose `id`, `name`, `enabled`, `config`, `hasPassword`, `hasAuthBody`, `createdAt`, `updatedAt` and `lastCheck`. The presence flags do not reveal secret values. A list response populates `lastCheck` with `{ startedAt, success, error, durationMs }`; the bare record returned after saving has `lastCheck: null`, so clients should refresh the list for current history.

`GET /api/projects` wraps the list as:

```text
{
  projects: Project[],
  nextExecution: ISO8601 UTC string,
  lastScheduled: null | { startedAt: epochMilliseconds, finishedAt: epochMilliseconds | null }
}
```

`GET /api/checks` returns `{ checks: [...] }`. Each row contains `id`, `projectId`, `projectName`, `startedAt`, `trigger`, `success`, nullable `error` and `durationMs`.

`nextExecution` is the pending scheduled date, advanced from the latest completed cron slot only after `finished_at` is recorded. It can remain in the past for a missing or incomplete run. Manual checks do not advance it. Before any cron run, the first project registration anchors the initial date; an incomplete first run retains its attempted slot. A completed batch may contain failed check results.

A persisted manual check returns `id`, `projectId`, `startedAt`, `trigger`, `success`, `error` and `durationMs`. An external failure is still a completed Nudge execution: the API returns HTTP 200 with `success: false`.

Cron returns `{ duplicate, slot, checked, succeeded, failed }`. Counts describe work performed by that invocation, not a cumulative total for the week. A completed duplicate returns zero counts.

## Error status reference

| Status | Meaning                                                                             |
| ------ | ----------------------------------------------------------------------------------- |
| 400    | Invalid JSON, missing/invalid fields or configuration validation failure            |
| 401    | Missing/expired session, wrong administrator password or invalid cron authorization |
| 403    | Browser origin is not trusted                                                       |
| 404    | Project or endpoint not found                                                       |
| 405    | Cron endpoint called with a method other than GET                                   |
| 409    | Another execution holds the lease, or project capacity is reached                   |
| 413    | Incoming JSON exceeds 32 KB                                                         |
| 415    | Browser write does not use JSON content type                                        |
| 429    | Login attempts exceed the current bucket limit                                      |
| 500    | Unexpected server/database/configuration failure; response details are suppressed   |

The router does not provide a uniform 405 response for every unsupported method; unmatched management routes ultimately return an authenticated 404.
